## Требует действия немедленно

Три тикета описывают эксплуатируемые без аутентификации дыры в живом проде. Все три подтверждены чтением кода.

### #1935 — вход под администратором без аутентификации

`POST /dev-login` зарегистрирован в общей locale-группе без гварда окружения; обработчик выполняет `Auth::login(User::admins()->first())`. Скрыта только кнопка в навигации (`@if app()->environment('local')`), сам маршрут в проде доступен. `middleware('guest')` не мешает — атакующий и так неаутентифицирован, а CSRF-токен берётся с любой публичной страницы.

### #1938 — выгрузка всей базы без прав

`ExportController extends AdminController`, но переопределяет `__construct` и не вызывает `parent::__construct()` — middleware `can:access-admin` не навешивается. На группе админских маршрутов собственной защиты нет. `store()` отдаёт CSV с `users` (все email), `solutions`, `comments`, `activity`.

**Severity повышена: high → critical.** Один анонимный запрос — полная выгрузка пользовательской базы с email. По воздействию это на уровне #1935 и напрямую усугубляет весь блок 152-ФЗ.

Корневая причина шире одного контроллера: гейт живёт в конструкторе базового контроллера и ломается молча при переопределении конструктора в наследнике. Фикс должен переносить защиту на уровень группы маршрутов.

### #1936 — побег из песочницы Racket → RCE

Код студента вставляется через `{!! $solution !!}` в текст `#lang racket`-модуля, то есть читается ридером Racket на уровне файла. Лимиты `racket/sandbox` применяются только внутри evaluator'а; ввод, закрывающий окружающие скобки, выносит формы на верхний уровень, где security-guard отсутствует. ОС-изоляции нет — `timeout 20s racket <file>` в шелле, без контейнера и seccomp.

Цепочка от анонимного запроса замкнута: маршрут проверки решения не требует аутентификации (#1937), а `GET /api/exercises/{id}` отдаёт тесты и эталон.

### Расхождения с текстом тикетов

**#1940 — severity завышена (high → medium).** Тикет упоминает `throttle:10,1` на маршруте проверки, но оценивает его как несущественный. При таком лимите для насыщения воркеров нужна ротация IP, то есть заметный ботнет — это отличает тикет от #1935/#1936/#1938, где хватает одного запроса. Попутно: `sandbox-eval-limits` равен `(list 10 128)`, то есть практический потолок ближе к 10 с, а внешние `timeout 20s` срабатывают только при зависании вне eval.

**#1939 — один пункт не подтвердился.** Утверждение «soft-deleted аккаунт молча восстанавливается» на текущем коде недостижимо: хук `deleting` в модели `User` обнуляет `email` до мягкого удаления, поэтому `firstOrNew(['email' => $email])` не может найти удалённый аккаунт. Ветка `if ($user->trashed()) { $user->restore(); }` мертва. На severity не влияет — захват живого аккаунта подтверждён полностью.

**#1946 — механика другая, чем описано.** Контроллер переопределяет только `sendResetLinkResponse()`. Ветка неуспеха осталась стандартной и завершается `ValidationException` с возвратом на форму. Различие проходит не по тексту сообщения, а по коду ответа и адресу редиректа — перечисление пользователей работает, но чинить надо не то, что указано в тикете.

**#1947 — природа проблемы другая.** `finish()` для гостя даёт `auth()->user() === null`, дальше `$user->increment('points')` падает. Это 500 и шум в Sentry, а не завершение главы без входа. Эскалации привилегий нет — есть незащищённый маршрут, роняющий приложение. Вывод (нужен `auth`) не меняется.

**#1945 — переведён в `needs-info`.** Техническая часть тривиальна, но нерешён продуктовый вопрос: на какие именно действия вешать `verified` и что делать с существующими пользователями без подтверждённого email. Плюс до закрытия #1939 подтверждённость обходится входом через OAuth — контроллеры проставляют `email_verified_at = now()` без проверки verified-статуса у провайдера.

### #1952 — заголовок упрощает, тело точно

Тело тикета описывает механику верно («обнуляет часть колонок, но контент решений/комментариев/activity-лога и часть строк сохраняются»). Заголовок — «ПДн физически остаются» — упрощает так, что может увести реализацию не туда, поэтому уточняю.

Хук `deleting` в модели `User` **физически обнуляет** контактные ПДн до мягкого удаления: `name`, `email`, `github_name`, `remember_token`, `password`, плюс сбрасывает `is_admin`. Эта часть уже сделана.

Дальше вызывается `->delete()` на связях: `comments`, `solutions`, `chapterMembers`, `exerciseMembers`, `activities`. **Все эти модели используют `SoftDeletes`** (проверено: `Activity`, `ChapterMember`, `Comment`, `ExerciseMember`, `Solution`, `User`). Строки остаются в базе вместе с содержимым: тексты комментариев, код решений и — с учётом #1955 — полные копии комментариев в `properties` записей `activity_log`.

Практический вывод для постановки: работа не в том, чтобы затирать поля пользователя (это уже есть), а в том, чтобы решить судьбу пользовательского контента и записей активности. Это продуктовое решение — комментарии участвуют в чужих обсуждениях, и их физическое удаление рвёт ветки.

Побочный эффект того же хука: поскольку `email` обнуляется, ветка восстановления soft-deleted аккаунта в OAuth-контроллерах недостижима — см. поправку к #1939.

### #1957 — код-часть уже выполнена по умолчанию

Тикет требует «включить PII-scrubbing в Sentry (`send_default_pii=false`, чистка breadcrumbs/SQL)». В `config/sentry.php` эти значения уже безопасны по умолчанию:

- `'send_default_pii' => env('SENTRY_SEND_DEFAULT_PII', false)`
- `'sql_bindings' => env('SENTRY_BREADCRUMBS_SQL_BINDINGS_ENABLED', false)`

Остаётся один вопрос, который нельзя решить из репозитория: не переопределены ли эти переменные в env на проде. Это надо проверить в Heroku — до тех пор код-часть тикета висит на `needs-info`. Претензия по почтовому драйверу тоже требует проверки прод-конфига, а не кода.

Организационная часть тикета (основание трансграничной передачи, реестр обработчиков, раскрытие получателей) остаётся в силе.

## Расхождения кода с документацией

Раздел Security в `CLAUDE.md` описывает поведение, которого в коде нет:

> Temp solution files are named with a random identifier and deleted after the check.

Ни одно из двух утверждений не выполняется. Имя файла — `hash('sha256', implode('', [time(), $exercise->id]))`, без случайной компоненты; удаления нет ни при успехе, ни при ошибке, плановой очистки тоже нет (#1941).

Там же:

> memory 256 MB, CPU 128 s

В шаблоне песочницы стоит `sandbox-eval-limits (list 10 128)` — это 10 секунд и 128 МБ. Значение 256 МБ относится к `sandbox-memory-limit`, а «128 s» не соответствует ничему.

Это стоит поправить вместе с фиксом #1941: документация, расходящаяся с кодом, вводит в заблуждение и людей, и агентов, которые её читают как источник истины.

## Отдельная находка вне тикетов

При проверке #1958 выяснилось, что прямое навешивание Laravel-овского `encrypted` cast на `email` **сломает аутентификацию**: cast шифрует со случайным IV, поэтому одинаковые значения дают разный шифротекст. Это ломает уникальный индекс, `firstOrNew(['email' => ...])` в обоих OAuth-контроллерах, вход и восстановление пароля. Если тикет возьмут в работу по букве заявки, поломка гарантирована — в комментарии к #1958 описаны три рабочих варианта.
